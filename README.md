# WukongBenchRunner

Консольная утилита на C# (.NET 8) для автоматического запуска **Black Myth: Wukong Benchmark Tool** из Steam.
Утилита выполняет два прохода: **CPU-тест** и **GPU-тест**. Для каждого она сама применяет настройки, запускает бенчмарк, проходит его меню, дожидается результата, разбирает его и выводит отчёт с характеристиками ПК.

```
WukongBenchRunner.exe     →  бэкап конфига → CPU-настройки → прогон → GPU-настройки → прогон → восстановление конфига → отчёт
```

## Быстрый старт

**Требования:** Windows 10/11 x64, Steam, установленный [Black Myth: Wukong Benchmark Tool](https://store.steampowered.com/app/3132990/) (бесплатно, ~8 ГБ).

1. Запустите бенчмарк **один раз вручную** и закройте его. При первом запуске он создаёт конфиг и компилирует шейдеры.
2. Скачайте `WukongBenchRunner.exe` со страницы [Releases](../../releases). Это один файл, .NET устанавливать не нужно.
3. Запустите его из любой папки:

   ```
   WukongBenchRunner.exe
   ```

4. Около 10–15 минут **не трогайте мышь и клавиатуру**: утилита сама нажимает кнопки в меню бенчмарка.

Отчёт выводится в консоль и сохраняется в `results/<дата_время>/`:

| Файл | Что внутри |
|---|---|
| `report.md` | характеристики ПК, результаты и настройки обоих тестов (удобно читать) |
| `report.json` | то же в машиночитаемом виде |
| `cpu_raw.json`, `gpu_raw.json` | исходные файлы результатов самого бенчмарка |

### Параметры

```
--dir <путь>              папка бенчмарка (по умолчанию ищется во всех библиотеках Steam)
--only <cpu|gpu>          выполнить только один проход
--timeout <минуты>        таймаут одного прохода (по умолчанию 15)
--output <путь>           куда сохранить отчёт (по умолчанию ./results)
--from-results <cpu.json> <gpu.json>
                          построить отчёт по готовым файлам, не запуская бенчмарк
```

### Сборка из исходников

Нужен [.NET 8 SDK](https://dotnet.microsoft.com/download) или новее.

```
dotnet run --project src/WukongBenchRunner
dotnet test
```

Чтобы посмотреть отчёт без Windows и без игры (работает и на macOS/Linux), используйте примеры из `samples/`:

```
dotnet run --project src/WukongBenchRunner -- --from-results samples/cpu_sample.json samples/gpu_sample.json
```

## Как это работает

| Шаг | Как сделано |
|---|---|
| **Поиск бенчмарка** | Путь к Steam берётся из реестра (`HKCU\Software\Valve\Steam`), список библиотек из `steamapps\libraryfolders.vdf`, имя папки из `appmanifest_3132990.acf`. Поэтому бенчмарк находится и на другом диске. |
| **Изменение настроек** | `b1\Saved\Config\Windows\GameUserSettings.ini`. Настройки хранятся в двух местах сразу: в `UISettingData` (то, что показывает меню, значения 1–5) и в `[ScalabilityGroups]` (группы качества Unreal Engine, `sg.* = значение меню − 1`). Утилита пишет в оба, иначе при старте одно перезапишет другое. Меняются только нужные ключи, остальное (яркость, звук и т. д.) остаётся байт в байт. |
| **Запуск** | `b1.exe` через `Process.Start`. Ключа командной строки, который сразу запускает тест, у бенчмарка нет, поэтому меню проходится эмуляцией ввода (WinAPI `SendInput`): Enter на заставке → «Тест быстродействия» → «Подтвердить». Координаты кнопок заданы в долях окна и не зависят от разрешения. Нажатия уходят, только если окно бенчмарка активно. |
| **Ожидание результата** | Каждый завершённый прогон бенчмарк записывает в `%TEMP%\b1\BenchMarkHistory\Tool\<unix-время>` JSON с итогами и примерно 10 000 покадровых замеров. Утилита запоминает уже существующие файлы и ждёт новый. Файл, который ещё дописывается, не распарсится, и утилита проверит его на следующем шаге. |
| **Завершение** | Процесс завершается через `Kill`, а не штатно: при обычном выходе игра сохраняет свои настройки поверх нашего ini. |
| **Восстановление** | Исходный `GameUserSettings.ini` возвращается в любом случае: после успеха, при ошибке и по Ctrl+C. Если утилиту убили, при следующем запуске она найдёт оставшийся бэкап и восстановит его. |
| **Характеристики ПК** | WMI (`Win32_Processor`, `Win32_VideoController`, `Win32_PhysicalMemory` и т. д.). Объём видеопамяти читается из реестра драйвера (`HardwareInformation.qwMemorySize`), потому что в WMI поле `AdapterRAM` 32-битное и обрезается до 4 ГБ. |

## Выбор настроек

Общее для обоих тестов: полноэкранное окно, **VSync выкл**, **ограничение FPS выкл**, **генерация кадров выкл**, размытие в движении выкл.
Без этого FPS упирался бы в частоту монитора или завышался бы дорисованными кадрами.

### CPU-тест: убрать видеокарту из уравнения

| Настройка | Значение | Почему |
|---|---|---|
| Разрешение | 1280×720 | минимальное в списке |
| Масштаб рендеринга | 50% | GPU рисует всего ~640×360 пикселей |
| Все параметры качества | Низкое (1/5) | тени, GI, отражения и постобработка — это работа GPU |
| Трассировка лучей | выкл | нагружает только GPU |

Время кадра на видеокарте становится в разы меньше, чем на процессоре. Игровая логика, анимация, физика и подготовка draw calls от разрешения не зависят, поэтому итоговый FPS определяется процессором.

### GPU-тест: максимальная нагрузка на видеокарту

| Настройка | Значение | Почему |
|---|---|---|
| Разрешение | 1920×1080 | верхний пункт списка разрешений |
| Масштаб рендеринга | 100% | апскейлер не снижает внутреннее разрешение |
| Все параметры качества | Кинематографическое (5/5) | максимальная нагрузка на шейдеры, тени, освещение, растительность |
| Генерация кадров | выкл | вставленные кадры скрывают реальную скорость GPU |
| Трассировка лучей | выкл | см. ниже |

**Почему без трассировки лучей.** RT поддерживается не всеми видеокартами, а неподдерживаемое значение в конфиге роняет бенчмарк при старте. Без RT тест одинаково работает на любой видеокарте, и результаты можно сравнивать.

### Как проверяется, что настройки применились

Бенчмарк сам записывает в файл результата, с какими настройками он отработал (`QualityLevel`, `ScreenResolution`, `Rtx`, `InsertFrame`). Утилита сверяет их с заказанными и показывает предупреждение при расхождении.
Кроме того, по покадровым `CPUFrameTime` и `GPUFrameTime` считается **узкое место**: какая доля кадров ограничена процессором. В CPU-тесте ожидается «CPU», в GPU-тесте «GPU». Это прямая проверка того, что настройки делают то, что должны.

## Метрики в отчёте

| Метрика | Источник |
|---|---|
| Средний / мин. / макс. FPS, FPS 95% | из JSON бенчмарка (`FPSAvg`, `FPSMin`, `FPSMax`, `FPS95`) |
| Средняя загрузка CPU / GPU | из JSON бенчмарка (`CPUAvg`, `GPUAvg`) |
| 1% low | считается по покадровым данным (`Records[].FrameRate`, перцентиль методом ближайшего ранга) |
| Среднее время кадра CPU / GPU, узкое место | считается по `Records[].CPUFrameTime` / `GPUFrameTime` |

## Архитектура

```
src/WukongBenchRunner/
├── Program.cs              точка входа: аргументы, сборка зависимостей, Ctrl+C
├── BenchmarkSession.cs     основной сценарий: бэкап → профили → восстановление
├── Profiles/               CPU/GPU профили и обоснование настроек
├── Config/                 правка GameUserSettings.ini (IniDocument, UISettingData, бэкап)
├── Discovery/              поиск бенчмарка через Steam
├── Running/                запуск процесса, проход меню (SendInput), ожидание результата
├── Results/                парсинг JSON бенчмарка и расчёт метрик
├── SystemInfo/             характеристики ПК (WMI)
└── Reporting/              консольные таблицы (Spectre.Console), report.md / report.json
```

Все зависимости от внешнего мира (процесс, ввод, файловая система с результатами, время) спрятаны за интерфейсами (`IBenchmarkProcess`, `IMenuNavigator`, `IResultSource`, `IGameConfig`, `ISystemInfoProvider`, `TimeProvider`). Поэтому весь сценарий покрыт тестами без запуска игры: таймауты, падение процесса, повторный запуск лаунчером, Ctrl+C, восстановление конфига, проход меню.

## Как велась разработка и проверка

Я разрабатывал решение на MacBook (macOS, Apple Silicon), а Black Myth: Wukong Benchmark Tool работает только на Windows. Поэтому сам бенчмарк я не запускал. Вместо того чтобы сдавать непроверенный код, я построил проверку так, чтобы закрыть как можно больше без реального железа:

- **Формат данных выяснен заранее.** Ключи конфига, путь и структура JSON с результатами, имена процессов и устройство меню взяты из открытых описаний, проверенных на реальных прогонах. Наугад не подбиралось ничего: некорректное значение в конфиге роняет бенчмарк.
- **Всё внешнее эмулируется в тестах.** Процесс, ввод, время и папка с результатами спрятаны за интерфейсами. Поэтому весь сценарий проверяется на фейках: игра не запустилась, лаунчер перезапустил процесс, результат дописывается частями, таймаут, Ctrl+C, сбой посреди прогона. Во всех этих случаях проверяется, что исходный конфиг восстановлен.
- **Реальные файлы на реальных форматах.** Правка ini проверяется на образце `GameUserSettings.ini`, в том числе в UTF-16 и с CRLF, как его сохраняет Unreal Engine. Парсер проверяется на файлах в формате бенчмарка.
- **Windows-часть проверяется на настоящей Windows.** В GitHub Actions на `windows-latest` все тесты прогоняются заново, сбор характеристик через WMI проверяется на реальной машине, и собирается `.exe` для Releases.
- **Безопасность по умолчанию.** Если что-то пойдёт не так на незнакомом ПК, утилита не оставит бенчмарк сломанным: она завершит его, вернёт настройки пользователя и напишет понятную ошибку.

Единственное, что можно проверить только вживую, — точное положение кнопок в меню бенчмарка. Оно вынесено в `MenuLayout` и описано ниже.

## Ограничения

- Положение кнопок меню (`MenuLayout`) рассчитано на текущую версию бенчмарка. Если обновление изменит меню, утилита завершится по таймауту с понятной ошибкой, а конфиг будет восстановлен.
- Список разрешений в меню зависит от монитора, поэтому индекс разрешения может указывать на другой пункт. Фактическое разрешение берётся из файла результата и показывается в отчёте, а при расхождении выводится предупреждение.
